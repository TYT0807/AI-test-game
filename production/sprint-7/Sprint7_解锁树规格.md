## §1 · 8 项解锁物完整表

**模型**：增量模型（Model B）。基础 **14 升级 / 10 遗物 / 4 武器不建任何解锁节点** → 永远默认可用、永远在池里；解锁树只呈现 **8 项新增内容**。解锁 = **池扩容**，不是**围栏**。

**红线**：解锁物**只进池**，一律**不写玩家初始数值字段**，只在局内被抽到/捡到时生效，局末清零。

**价格合计 = 500 结晶**（40×3 + 60×3 + 100×2）。
**依赖图**：三条独立链（升级 3 / 遗物 2 / 武器 3），同链线性、无环、无孤儿、跨链无依赖。

> ⚠️ **`max` 有两个，不要混**：
> - **节点 `max`**（本表）= 该节点**可购买次数**，全部 = 1（一次性）。
> - **池条目 `max`**（§2）= 该升级**在一局内可被取的最大次数**（`upgrades.gd` 权重 = `(max - taken) × rarity`）。3 个新 upgrade 的池条目 `max` **必须 = 1**。
>   `max=0` → 权重恒 0 → **永久抽不到且不报任何错**；`max>1` → 一局能拿 2–3 次 → 强度失控。

### §2.4 `"meta"` 字段的职责（**运行时门控 vs 自检交叉校验，两回事**）

> **`"meta"` 字段的职责（team-lead 裁定，v2.10）**
>
> - **运行时门控只读 `meta.gd:UNLOCKS` 一张表**：由节点的 `kind` + `target` 推导「这条内容是否被锁」，代码侧建反查索引（`"kind:target"` → 节点 id）。**三个池的数据表不需要为了门控而携带任何字段。**
> - **池条目的 `"meta"` 字段是「自检用的冗余交叉校验」，运行时不读它。** 启动自检会核对：它指向的节点存在 → 该节点的 `kind` 与所在池一致 → 该节点的 `target` 等于本条目的 `id`。**三者任一不符 → 启动即报错。**
> - **为什么不删掉它**：外键一旦与 `UNLOCKS` 不同步，**表推导不会出错**（运行时根本不读它），但**自检会报错** → 漂移被抓住而不是被藏起来。**外键从「行为依赖」降级为「断言面」，失败方向永远是「宽松」而不是「卡死」。**
> - **推论（不变）**：池里**没有对应节点**的条目 → **默认可用**（永远在池里）；新加内容忘建节点的后果是「立刻可用」，**不是「永久锁死玩家」**。

**为什么这样比任一纯方案都稳**：
| 纯方案 | 失效方式 |
|---|---|
| 只用外键（池条目带 `meta`、运行时直接读它） | 外键写错 → **玩家买了却进不了池**（行为性故障，且要等玩家触发才发现） |
| 只用表推导（池条目完全不带字段） | 表推导**永不失效**，但「池条目与解锁表对不上」这件事**没有任何地方能发现**（漂移被藏起来） |
| **本方案（表推导门控 + 外键断言面）** | 运行时靠表推导 → **不可能卡死玩家**；外键对不上时**自检立刻报错** → 漂移在启动时就被抓住 |

**§1 的红线完全不受影响**：「解锁物只进池、一律不写玩家初始数值字段」照旧成立。

### §2.5 武器候选池与 `rifle` 的特殊地位

**`rifle` 是起始武器，恒可用、不进 `DROP_POOL`、不受解锁门控。** 这一点必须写死，否则「武器候选 ≥ 2」这类判据会误判。

代码现状（实读 `weapons.gd`）：
| 函数 | 集合来源 | 是否含 rifle |
|---|---|---|
| `Weapons.unlocked_ids()`（`:45-50`） | 遍历**全部** `DEFS` | **含**（注释已写「rifle 永远可用」） |
| `Weapons.random_unlocked()`（`:55-62`） | 只遍历 **`DROP_POOL`** | **不含** |

> `DROP_POOL` 的注释已写明「可掉落 / 可上架的武器池（**不含起始武器 rifle**）」。
> → **两个集合本来就不是同一个集合**：`unlocked_ids()` ⊋ `random_unlocked()` 的候选集。

**因此判据要分两层，不能只看一个**：

| 判据 | 正确写法 | 为什么 |
|---|---|---|
| **玩家可用武器总数** | `Weapons.unlocked_ids().size() ≥ 2`（**含 rifle**） | 这才是「玩家是不是被卡住」的真问题。默认档 Model B 下 = rifle + shotgun + railgun + launcher = **4** ✅ |
| **掉落 / 商店的候选多样性** | `Weapons.random_unlocked()` 的候选集 **≥ 2** | 单独看会误判：若某状态下只剩 1 把非 rifle 武器，候选 = 1，但玩家实际有 rifle + 那把 = 2 把，**并不卡** |
| **不变量** | `Weapons.random_unlocked()` 的返回值 **∈** `unlocked_ids()` | 防掉落出一把玩家没解锁的武器 |

> ⚠️ 只断言「`random_unlocked()` 候选 ≥ 2」会在合法状态下误报 FAIL；只断言「`unlocked_ids().size() ≥ 2」则抓不到「掉落池被清空」这种退化。**两条都要，且互相交叉。**

**本轮换表要求**：`DROP_POOL` 需加入 3 把新武器（`mw_swarm` / `mw_arc` / `mw_cluster`）；**`rifle` 不加**。`Weapons.random_unlocked()` 已存在，**由它统一过滤未解锁武器**。
`game_main.gd:623` 与 `pickup.gd:153` **两处调用点已统一委托到 `Weapons.random_unlocked()`** → 无需再改（见 §12）。

## §3 · 经济公式与常量

### §3.1 常量（`meta.gd:ECONOMY`）

```gdscript
const ECONOMY := {
	"rate": 0.10,          # 局内累计拾取 → 局外源石
	"floor_bonus": 8,      # 每深入 1 层的额外奖励（按层数-1 计）
	"kill_bonus": 0,       # 击杀与源石高度相关，再计一次 = 同一件事算两遍
	"run_cap": 60,         # 单局结算上限（防刷）
	"min_floor": 1,        # 不设层数门槛（设 2 会让弱玩家永久卡死，见 §4.3）
	"min_seconds": 45.0,   # 短于此不结算
}
```

### §3.2 公式

```gdscript
payout = clamp(
    floor(diamonds_earned * rate
        + (max_floor_reached - 1) * floor_bonus
        + kills * kill_bonus),
    0, run_cap)
```

**两个口径细节（用例必须锁死）**：
1. **`diamonds_earned` = 本局「累计获得」的源石总数，消费不扣。**
   必须由 `game_state.gd` 的 `add_diamonds()`（现 `game_state.gd:112`）累加得到。
   **不得用 `Game.diamonds` 减起始值** —— `barren` 因子开局会 `add_diamonds(10)`（`game_main.gd` 的 `_roll_modifier()`），差值法会漏算或算负。
   （现状：`game_state.gd` 已有 `run_diamonds_earned` 与 `meta_spent` 两个计数器，口径正确。）
2. **`max_floor_reached` = 本局到达过的最深层数**，不是死亡时的当前层。

### §3.3 各档产出（按实跑源石口径反推）

| 结局 | 局内源石 | 层 | 杀 | 计算 | payout |
|---|---|---|---|---|---|
| 45 秒内秒退 | — | — | — | < min_seconds | **0** |
| 1 层死 | 60 | 1 | 20 | 6 + 0 | **6** |
| 到 2 层 | 110 | 2 | 45 | 11 + 8 | **19** |
| 到 3 层 | 200 | 3 | 90 | 20 + 16 | **36** |
| 到 4 层 | 300 | 4 | 130 | 30 + 24 | **54** |
| 到 5 层+ | 400+ | 5 | 160+ | 40 + 32 | **60（封顶）** |

## §4 · 结算与弃局口径

### §4.1 三种结局

| 结局 | settle reason | 是否结算 | 说明 |
|---|---|---|---|
| 死亡 | `death` | **结算** | 局外源石是「完成一局」的奖励 |
| 暂停 → 回主菜单（主动退出） | `quit` | **不结算** | 没完成一局就不发；同时是防刷分的关键 |
| 进程崩溃 / 强杀 | — | 不结算 | 没跑到结算就没入账 |

死亡后按 R 重开 → **旧局已结算，新局重新计数**。需 per-run 标志保证**只入账一次**（现状：`game_main.gd` 已有 `_run_settled`）。

### §4.2 退出确认框（team-lead 裁定 1）

> **主动退出必须弹确认框，不能静默扣钱。**

- 触发：暂停菜单「回主菜单」点击后
- 标题：**「退出本局？」**
- 正文：**明确写出本局将损失约 N 结晶**（N 按 §3.2 正式公式，用当前 `diamonds_earned` / `max_floor_reached` 预估）
- 按钮：`确认退出` / `取消`
- 确认 → 退出且**不结算**（reason = `quit`）；取消 → 留在局里
- `min_seconds = 45` 不满足时同样要提示（本来就不给结算）

**理由**：知情扣钱 = 一次正常的风险决策；静默扣钱 = 惩罚。玩家濒死时不敢退出，挫败感最大化。

### §4.3 `min_floor = 1`（硬伤，不可回调）

`min_floor = 2` 会造成**弱玩家永久卡死**：
> 一直死在一层的玩家拿不到任何结晶 → 永远解锁不了任何东西 → 实力永远不涨 → 死循环。

meta 系统必须有「越弱越能爬」的通道。防刷由 `run_cap = 60` + `min_seconds = 45` + 「每次开局都是全新随机地牢」承担（本来就不存在刷同一张图的可能）。

### §4.4 结算面板

现状 `hud.gd` → `game_over(extra)`（现 `hud.gd:696-702`）已预留 extra 追加位，**只需拼内容**：

本局源石 213            本局结晶  +28      ← 金色 Color(1.0,0.82,0.42)，font 20

## §6 · `perk` 的定义与红线

team-lead 裁定 2，本轮 8 项**全部是 upgrade/relic/weapon，不用 `perk`**，但该槽位语义现在定死：

> **`perk` = 不进抽卡池、但局内必定生效一次的解锁物。**
> 它改变**开局流程**（例：开局额外给一张随机升级卡 / 开局必定获得一件遗物），但**仍然不写玩家初始数值字段**。

### 红线（不可协商）

1. **解锁物一律不写玩家初始字段**，只在局内被抽到/捡到时生效，局末清零。
2. **真正的「永久数值加成」不管叫什么 kind 都不做**（全局 +10% 伤害 / +1 生命上限 / 永久浮游炮 / 永久初始弹匣 +1）。
3. 理由：永久数值 → 后期必然收敛到单一最优 build，肉鸽「每局不同」的根基被抹平；解锁页会退化成「加攻击力」的 Excel。

### 同样禁止的做法

| 不建议 | 原因 |
|---|---|
| 解锁物默认每局自动生效、不进抽卡池 | 随机性归零，游戏变成固定 build 刷层 |
| 解锁卡权重高于同级基础卡 / 保底必出 | 复利雪球：解锁越多越强 → 越解锁越不想玩别的 |
| 结晶可退款 / 洗点 | 树的前置结构失效，决策变成零成本试错 |
| 用「局内剩余源石」折算结晶 | 惩罚在商店消费，把正确行为变成错误行为 |
| 局外结晶可兑换局内源石 | 局内经济被局外污染，单局平衡失效 |
| 一次性打包解锁整条分支 | 「树」退化成 3 个开关，前置结构无意义 |
| 解锁页给「推荐购买 / 最优解」 | 替玩家做决策，抹杀流派个性 |
| 解锁页做成纯数值对比表（Excel 感） | 把体验做成计算题，丢失探索感 |

### §8.E 世界随机性与 meta 解耦（**硬判据**）

> **解锁任意数量的项后，同种子的第 2 层及以后的地图（房间坐标集 / 房型序列 / 门连接）必须与未解锁状态完全一致；允许不同的只有「升级抽取结果」与「战利品抽取结果」。**

#### §8.E.1 测什么（**别测错对象**）

| 项 | 规定 |
|---|---|
| **代码** | **同一份代码**（同一个构建、同一次编译） |
| **种子** | 同一个 `run_seed` |
| **两档** | **全新档**（一个都没解锁）**vs 全解锁档**（`SMOKE_META_UNLOCK=all`） |
| **比较对象** | **每一层**的地图指纹：`rooms=`（房间坐标集）与 `kinds=`（房型序列 + 门连接）**逐字 diff 为空** |
| **允许不同** | 只有「升级抽取结果」与「战利品抽取结果」 |

> ❌ **不是**比「SPR6 冻结版 vs SPR7」这类**不同代码版本**之间的地图 —— 那是版本差异，不是本判据要测的东西。**跨版本比较不属于 §8.E。**

#### §8.E.2 为什么是硬判据
1. `game_main.gd` 的 `DungeonClass.generate(floor_num, Game.rng, size)` 把**全局流**传进地图生成 → 地图与升级抽取 / 掉落共用一条随机流 → 解锁项入池改变 `Upgrades.roll()` 的权重总量 → 抽到不同的卡 → 击杀/掉落次数变 → **随机流位置漂移** → 第 2 层起地图结构改变。
2. **单纯把抽卡拆出去不够**：相机抖动每帧无条件消费随机数 → 地图流位置是**帧数的函数**；而 build 变强 → 战斗更快 → **到达第 2 层的帧数不同** → 第 2 层生成前的地图流位置不同 → 第 2 层地图结构**照样改变**。
3. **正解：每层地图用「由 (run_seed, 层号) 派生」的独立 RNG**。`DungeonClass.generate()` 的第二个参数就是地图 RNG —— 只要传一个每层派生的独立 rng，**第 N 层地图就只由 (run_seed, N) 决定**，与帧数、战斗节奏、解锁内容完全无关。**第 1 层与第 2 层都用派生 rng。**
4. 这条同时保护 Sprint 6 的固定种子基线（过门 6–17 / loop 0）不被 meta 层打破，也是 §8.B 的 A/B 对比能成立的前提。

#### §8.E.3 实现约束（**三条，缺一则 §8.E 不可判定**）

| # | 约束 | 理由 |
|---|---|---|
| **1** | **地图生成必须使用「由 `(run_seed, 层号)` 派生」的独立 RNG**，与玩法流完全无关 | 第 N 层地图只由 `(run_seed, N)` 决定 → 与帧数、战斗节奏、解锁内容**完全无关** |
| **2** | **表现层随机（相机抖动 / 粒子 / UI 闪烁）不得消费玩法随机流**；且**游戏逻辑计时不得依赖真实 delta** | 否则同一 `run_seed` 的两次运行会在**同一游戏时刻**处于不同的随机流位置 → 地图指纹不可复现 → **§8.E 无法判定** |
| **3** | **不得用「保证消耗 N 次随机数」来维持稳定**。已实测（Godot 4.7.2）：`randi_range(0, 0)` **不消耗**随机流，而 `randf_range(0, 0)` **消耗** —— **两个 API 行为不一致** → 凡是要「保证消耗 N 次」的地方**不能用 `randi_range(0,0)` 兜底**。任何**条件性消耗**都会让共享流的推进位置成为**运行时状态的函数** | 约束 3 是约束 1 的**反面教材**，不是它的替代品 |

> ⚠️ **`--fixed-fps 60` 单独不足以保证可复现**
>
> 帧率固定了 delta 的**分布**，但若表现层随机仍从玩法流消费、且逻辑计时仍按真实 delta 累加，同一 `run_seed` 的两次运行**仍会在同一游戏时刻处于不同的随机流位置**。
> **实测**：同种子 `--fixed-fps 60` 跑两次，**第 26 行起分叉**（`use_door` 89 vs 34），`t=` 序列不等差。
> → **必须同时满足约束 1 与约束 2**，光加 `--fixed-fps 60` 解决不了。

> **一句话**：**别去数随机数消耗了几次，去把地图的流从玩法流里摘出来，并把表现层随机与逻辑计时也摘出去。**

## §10 · 权重补偿与 `boost` 精确语义

### §10.1 为什么需要

解锁 = 池扩容 = 稀释。基础 14 张升级权重合计 ≈ 431，3 张新解锁升级合计 ≈ 15 → 基础占比 ≈ 96%，**稀释本身可忽略**。
但**单张新卡的可见度不够**：P(某张 rare 新卡每次抽中) ≈ 5/446 ≈ **1.1%**；一局约 7 次升级选择（每 3 选 1，共约 21 个卡位）→ **一局见到该卡的概率仅约 21%**。玩家花 40 结晶买的卡 5 局才见一次 = **解锁等于没买**。

### §10.2 两层补偿

| 规则 | 倍数 | 作用域 | 作用对象 |
|---|---|---|---|
| **稀释补偿** | **×1.5** | **永久**（该节点一旦解锁，一直有效） | 该节点对应的池条目 |
| **新解锁引导** | **×6** | **解锁后的前 3 局**（`boost` 字典控制） | **仅刚解锁的那一项** |

**叠加关系：乘性** → 新解锁的前 3 局 = `×1.5 × ×6 = ×9`；第 4 局起 = `×1.5`。
**只作用于升级池**（遗物与武器是均匀抽取，无权重概念）。

### §10.3 `boost` 的精确语义（QA 需求点，勿歧义）

**数据结构**（存在 `meta` 存档里，随 `crystals` / `unlocked` 一起落盘）：
```
meta["boost"] = {"u_mx_pierce": 3}     # 键 = 节点 id，值 = 「还剩几局享有 ×6」
```

**语义**：`{"u_mx_pierce": 3}` = **「还有 3 局享有 ×6 加成」**，即**包含解锁后的第 1 局**。

**状态机**：

| 时点 | 动作 | `boost` 值 | 该局抽卡时是否享 ×6 |
|---|---|---|---|
| T0 主菜单解锁 `u_mx_pierce` | 写入 | `3` | — |
| T1 第 1 局开始 | 不变 | `3` | **是**（×1.5 × ×6） |
| T1 第 1 局**结束** | 递减 | `2` | — |
| T2 第 2 局开始 | 不变 | `2` | **是** |
| T2 第 2 局结束 | 递减 | `1` | — |
| T3 第 3 局开始 | 不变 | `1` | **是** |
| T3 第 3 局结束 | 递减 → `0` → **删除该键** | 删除 | — |
| T4 第 4 局开始 | — | 不存在 | 否（只剩永久 ×1.5） |

**三条规则**：
1. **递减发生在「本局结束时」**，不是局初、也不是结算入账时。
2. **弃局（quit）也递减** —— 「3 局」就是 3 次尝试，弃局也算用掉一局；同时避免弃局刷 boost 时长。
3. **递减到 0 即删除该键**（不保留 0 值）。

**解锁入口唯一性**：解锁页只在主菜单开放，暂停菜单不开放 → 不存在「局中解锁、当前局立刻生效」的情况。

### §10.4 不做「保底必出」

不做「解锁后第一局必在第一个三选一里出现该卡」。理由：保底卡会占掉一次三选一机会、稀释其他卡的体验，且会形成「每局第一张是解锁卡」的固定预期，反而降低后续期待。权重方案已足够（可见度 21% → 约 76%）。

### §10.5 权重公式落点

`upgrades.gd` 的 `_weight()`（现 `upgrades.gd:74-77`）需改为：
```gdscript
static func _weight(p: Dictionary) -> int:
	var left := maxi(int(p["max"]) - int(taken.get(p["id"], 0)), 0)
	var w: int = int(RARITY_WEIGHT.get(p.get("rarity", "common"), 10))
	# 解锁卡稀释补偿 ×1.5（永久）
	# 新解锁引导 ×6（前 3 局，见 §10.3）
	return left * w
```

#### §11.2.1.1 `SMOKE_META_CORRUPT` 四种模式的实现要点（写错就触发不了断言）

| 模式 | 怎么写坏档 | 触发哪条路径 | ⚠️ 坑 |
|---|---|---|---|
| `missing_field` | **只写 `version`**，**缺 `crystals`/`unlocked`/`boost` 三字段**；读回时逐个补默认，并把**补了哪些字段名**填进 `%s` | 「缺字段 → 分别补默认」 | **不能写 `diamonds`** —— 那是旧字段名（§14.1 已定 `crystals`）。写 `diamonds` 会让「缺 `crystals`」与「多了个野字段」两件事混在一起 |
| `bad_type` | 写**不可解析的垃圾内容**，让 `cfg.load()` **返回非 OK** | 「读取失败 → 用默认值」 | **不是**写类型错的值！`ConfigFile.load()` 对「值类型错」**照样返回 OK**（`diamonds="不是数字"` 能正常加载，`int("不是数字")` 返回 0，不崩也不报读取失败）→ 那样写**永远触发不了**「读取失败」这条断言。`err=%d` 必须是**真实返回码** |
| `unknown_id` | `unlocked` 里塞不存在的节点 id | 「未知 id → 丢弃」 | ⚠️ 现有实现是**逐个 id** 报「存档里的未知解锁 id 已忽略：%s」（`game_state.gd` 的读档路径）。本节规定的是**计数式**「丢弃未知解锁 id %d 个」→ 实现侧需把逐 id 串**统一替换**为计数式（一处 warn，不要两种并存） |
| `bak_fallback` | 主档写成坏内容、同时存在可读的 `.bak` | 「主档读失败 → 回退 `.bak`」 | 该 WARN 措辞**已存在**（`game 主存档不可用，已回退 .bak`），无需新增文案，只需让探针能造出「主档坏 + .bak 可读」的组合 |

## §14 · 存档格式与持久化

> 本节补于 v2.4。此前存档结构只在 §10.3 出现过 `boost` 片段，完整格式缺位 —— 而它是 QA 会直接测的（M4 降级族 / M2-6 跨进程往返），「唯一权威源」不能有缺位。

### §14.1 文件与结构

**文件**：`user://meta.cfg`（ConfigFile，section `meta`）
**不与** `user://settings.cfg` 混用（后者是音量/震动/精简 HUD，混进进度会导致设置重置连坐进度）。

```
{
  "version":   1,                          # 存档结构版本；高于当前版本 → 保留原文件 + 用默认值 + WARN
  "crystals":  340,                        # 局外源石余额（int）
  "unlocked":  ["u_mx_pierce","mw_swarm"], # 已解锁节点 id 列表（**数组**，不是字典：每节点只能买一次）
  "boost":     {"u_mx_pierce": 2},         # 新解锁卡的权重加成剩余局数（见 §10.3）
  "stats":     {"runs":12,"best_floor":5,"best_kills":210,"total_time":4320}
}
```

> ⚠️ **字段名用 `crystals`，不要用 `diamonds`** —— 局内 `Game.diamonds` 已经叫 diamonds，存档里再出现一个 `diamonds` 就是两套口径串味（正是「两套来源同名最易 debug 串味」的典型）。

### §14.2 写入时机

| 时机 | 行为 |
|---|---|
| **结算入账** | 立即写盘（`ConfigFile.save()`），**不延迟到退出时** —— 玩家可能直接关游戏 |
| **购买解锁** | 扣费 → 入集 → 写盘；**写盘失败则回滚内存变更**（余额与解锁集复原 + 提示失败） |
| **局内 `reset()`** | **绝不能碰 `meta`** —— 局外进度跨局保留 |

### §14.3 降级要求（与 §8.D 呼应）

| 损坏形态 | 期望行为 |
|---|---|
| 文件不存在（首启） | 正常初始化：余额 0 / 解锁集空 / 默认集可用 |
| 主文件读失败 | 回退 `.bak`；再坏则用默认值 + WARN |
| 缺 `crystals` / `unlocked` / `boost` 字段 | 分别补默认（0 / 空数组 / 空字典），**其余字段保留** |
| `unlocked` 类型错（字典代替数组） | 降级为空数组 + WARN，不崩 |
| `unlocked` 含未知 id | **丢弃，绝不进池** + 自检报一条 |
| `crystals` 为负 | 夹取到 0 |
| `version` 高于当前 | 保留原文件 + 用默认值 + WARN |

**降级黄金判据**：任何坏存档启动都必须是「**0 SCRIPT ERROR + 0 条 `[ERR] meta:` + 余额回默认 + 空解锁集 + 有效升级池 ≥ 3**」五件套。

### §14.4 SMOKE 隔离

- SMOKE 探针只写隔离路径（`user://_smoke_meta.cfg`），**绝不碰玩家的 `user://meta.cfg`**。
- 隔离文件**进程首次读取前删除重建** → 保证连续两轮 SMOKE 的有效池完全一致（基线不漂移）。
- 跑完全部 SMOKE 后，玩家 `meta.cfg` 的**内容与 mtime 都不变**，且 `meta.cfg.bak` **不得存在**。

> 🔴 **删除条件只认「默认隔离路径常量」，不认「`user://` 下的任意路径」**
>
> 「跑前删除重建」**只允许在 `path == META_SMOKE_PATH`（默认隔离路径常量）时执行**；**自定义 `SMOKE_META_PATH` 指向的文件一律不得删除**。
>
> **为什么**：跨进程往返用例（`SMOKE_META_SAVE=1`，§11.2.1 第 6 行）依赖「第一个进程写出的文件被第二个进程**原样**读回」。若删除条件被写成「任何 SMOKE 路径在首读时都删」（例如「path 在 `user://` 下就删」），则**第二个进程会把第一个进程写的文件删掉** → 往返实际比的是「默认值 vs 默认值」→ **永远 OK → 假通过**。这种失败**不报错、只会让用例失去意义**，所以必须靠下面的断言拦住，而不是靠人肉看日志。
>
> **假通过防护（QA 必查）**：`[SMOKE-META] roundtrip=OK crystals=%d unlocked=%d` 中的 **`crystals` 必须 ≠ 0 且 `unlocked` 数量必须 ≠ 0**。若为 `0 / 0` → 说明文件被删、比对的是默认值 → **判 FAIL，不得记 PASS**。
>
> **当前实现**：删除条件已是 `path == META_SMOKE_PATH` 的**常量精确比较**（实读 `game_state.gd` 的 `load_meta()`），**行为正确**；本条是**防后续重构改错**（把它简化成「路径在 `user://` 下」就会假通过）。
