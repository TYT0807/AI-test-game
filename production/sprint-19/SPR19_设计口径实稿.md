## 〇、诊断与立场

- **本批是「加关系」，不是「加实体」**：`SHRINE_OFFERS` 10 条与 `FLAVOR` 的 10 条 `shrine/<id>` 手记都已存在，本批只是把它们接进已有的 `codex` 体系（新增一个分类维度，不新增房型 / 敌人 / 资源 / 输入动作）。定性成立。
- **S18 留下的空白**：D 灰字恒显被定性为「场所的持续性在场」（关联），C 走退化版后「发现度回报」这一层始终没人兑现；S19 补的正是这一层。
- **自我决定论落点**：本批主补**胜任**（10 种交换都做过 = 可累积的阅历与完成度），附带**自主**（只有我真正付过代价的才登记，曝光不算），轻**关联**（地窖把我做过的事留了一笔）。三者里「胜任」是主项，别写成「补自主」——收集完成度本质是胜任。
- **MDA**：M = 一次成功交换触发一次登记；D = 玩家为集齐 10 种会主动在圣所里选没试过的卡，与「永远选当期最优卡」形成张力；`min_floor` 分层（3/5/7）使高层卡低层不可得，迫使跨层 / 跨局规划；A = Narrative / Challenge。**这是本批真正的新决策情境**，不是图鉴多一行。

## 一、前置 1 · 发现口径裁定

**裁定：支持主理人倾向「玩家实际交换过」，不推翻。** 挂点取 `_on_shrine_chosen()` 内、`_shrine_execute(offer)` **成功返回之后**，与 `_echo_choices.append()` 同处（S16 抉择链同源同序）。

**复核理由（三条，含主理人未列的一条）**

1. **跨 GDD 一致性（新增论据，最强的一条）**：既有五类的登记语义全是**事件结果** —— `enemies` 已遇、`relics` 掉落即发现（S15 B 裁定）、`suffixes` 已获、`themes` 已历、`bosses` 已击败。没有一类是「系统把选项摆给我看过」。若算「三卡显示过」，登记的是 **rng 发过什么牌**，与五类口径不一致，是异类；「实际交换过」才与「我遭遇 / 获得 / 做过」同构。
2. **发现度稀缺性数学**：`floor >= 3` 每层 1 间 shrine、一次只选 1 张（`shrine_panel._pick()` 单选 emit），10 条又按 `min_floor` 3/5/7 分层 → 一局上限受层数约束、且高层卡低层见不到，全收集需**跨多局且刻意选不同卡**。反之「三卡显示过」一次进房登记 3 条，几局即满格 —— 正是 S18 已确立的判据「**跨局恒定或快速饱和的输出不该占位**」所否掉的形态，图鉴那行会秒变噪音。
3. **零实现代价**：`_echo_choices.append()` 已在正确时序上（`_shrine_affordable()` 双保险 → `_shrine_execute()` → 清房 → 登记），零新增事件源 / 零 rng / 零计时 / 零新输入；一次交换 = 一次抉择链记录 = 一次发现登记，天然对齐。

**我对挂点精度的两点补充（请写进实施规格）**

- 登记必须在 **`_shrine_affordable()` 通过之后**：置灰卡不可选，绝不能因"看过"而登记。
- 登记必须在 **`_shrine_execute()` 返回之后**：若执行链内部早退 / 异常，不应误登记「做过」。主理人草案写的是「支付双保险通过之后」，建议精确到这一步，落在 `_echo_choices.append()` 相邻行即可。

**「首见 vs 已见过」在卡面上要不要变化 → 裁定：不变，且建议明确写进红线。**
理由：① 本批边界已定「不改 S18 D 灰字恒显逻辑」，改了就是范围蔓延；② 若卡面按发现状态变色 / 加标记，等于把局外发现度**回注到局内决策界面**，玩家选卡时多一层「哪张还没登记」的算计，会压过「为生存而选」——同时踩**认知过载**与**主导策略**两条红线；③ 更要紧的：S18 D 的价值主张是「场所的持续性在场」，卡面随发现状态起伏就把这句定性又推翻了，文档与实现立刻不一致。**本批的发现度回报只走两个通道：局外图鉴页 + 瞬时首发现 toast；不碰卡面。**
未来若确要做「已登记」标记，正确位置是**图鉴页分区内**（如已发现名单加个符号），不是圣所卡面 —— 登记为后续候选，本批不做。

## 二、前置 2 · 播报 / 标题 / 显示名口径

### 2.1 kind 逐字 `shrine`（单数）—— 确认，并加一条正向断言

`mark_codex()` 播报取 `Data.FLAVOR.get(kind + "/" + id, "")`，S18 D 的 10 条键正是 `shrine/<id>`。写成 `shrines` 会全数查不到、**静默失败不报错**（`icon_codex` 同型坑）。草案负向对照③已列；建议再补一条**正向**断言：`mark_codex("shrine", <任一 id>)` 后 toast 文本确实含对应手记句 —— 不能只验 `codex["shrine"].size()` 或「键存在」，否则「表写了没接上」照样漏。

### 2.2 图鉴分组标题：裁定「已行抉择」，否掉「已识圣所」

- 既有五个标题是「已 + 动词 + 名词」同构：已遇敌人 / 已见遗物 / 已获词缀 / 已历主题 / 已击败 Boss，**动词对应各自的发现口径**。
- 「已识圣所」两处不合：① 「识」= 见过 / 认得，与「实际交换过」口径矛盾，且 S18 已否过「熟客 / 识」这类措辞；② **分母是 `SHRINE_OFFERS.size() = 10` 条交换条款，不是圣所房间数** —— 标题写「圣所」会让玩家误以为收的是房间。
- **推荐「已行抉择」**：动词「行」= 做过，对应「实际交换过」；名词「抉择」是项目既有术语（`SHRINE_OFFERS` 抉择圣所、S16 「抉择链」、`MILESTONES` 里「首入圣所 —— 抉择即构筑」），**不臆造设定**，四字与其余标题同构。备选「已换条款」（同样指条目不指场所）。
- 若主理人坚持别的措辞，只需替换 `_codex_section()` 的一个字符串参数，成本为零 —— 但请保留「动词对应交换、名词指向条款」这两条约束。

### 2.3 显示名来源：单源 `Data.SHRINE_OFFERS[id]["name"]`

与 `suffixes` / `themes` 同型：`_codex_section("shrine", <标题>, Data.SHRINE_OFFERS.size(), func(id): return String(Data.SHRINE_OFFERS[id].get("name", id)))`。分母单源取表长、不硬编码 10；`.get("name", id)` 兜底防未知 id 直出英文（与 `ENEMIES` / `RELIC_SUFFIXES` 分支同纪律）。
**隐性红利**：10 个 `name`（血祭 / 源石淬炼 / 净化 …）与 `FLAVOR` 10 句的首短句逐字一致，图鉴名单与手记不会显示漂移。**已知观察**：这两处文本是**双源**（`name` 字段 + 手记里手写的名字），本批不改、不新增同步机制，但请登记为观察项 —— 未来若改 `name`，手记首句不会自动跟随。

### 2.4 首发现播报文案：裁定「沿用 S18 那 10 句」，不另写

- **键已占用、零改动即可命中**：`mark_codex()` 的取键规则 `kind + "/" + id` 与 S18 D 的 `shrine/<id>` **天然对齐**，扩类后 10 句自动进入播报，无需新表、无需改 `mark_codex`、无需新登记面、无需新断言面。这是最纯粹的「加关系」。
- **语感天然一致**：那 10 句本来就是「废弃矿窟的实用主义」矿工手记，与 `bosses` / `themes` 的播报同前缀「矿工手记 · 」，零风格断层。
- **「复读」不是新问题**：S18 B 已让 `themes` 手记在层签**恒显**，而 `mark_codex("themes", rule)` 首发现时播报的是**同一句** `FLAVOR["themes/<rule>"]`。「恒显文案 + 首发现复读」是项目**已接受**的既定形态；shrine 沿用不引入新的不一致。
- **如实登记的已知取舍**：toast 的信息增量只在「这一条被收进图鉴」这个事实，不在文案新意；`flash_toast` 2.2s 单例会被后续 toast 覆盖 —— 单次交换只登记一条，天然绕开同帧互斥（在册观察②），但连续跨房交换仍会覆盖，属既有行为，本批不动。
- **若翻转裁定要另写**：`shrine/<id>` 已被 S18 灰字占死，新短句**不能复用这个键** → 必须新增一张发现集专用表 + 给 `mark_codex()` 加按 kind 分派的**特例分支**（改通用函数、增回归面、违反零实体）。这不是换字符串的成本。备选表见 §四，标为**不采用**。
