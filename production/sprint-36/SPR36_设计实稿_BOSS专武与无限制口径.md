## 4. 机制本体：作者这句话在游戏里到底是什么

### 4.1 一句话（rev2）

**「第一位漏洞」的体现不是"多一个解锁树"，而是"少一层门槛"——别人要靠结晶买的东西，他拿着就直接能用；而 BOSS 手里的东西本来就不是商品，是从它身上夺来的。**（叙事主体＝先贤，§1.3；⛔ 任何文案不许把这套机制说成苏瑾的能力。）

### 4.2 三层结构（表层叙事 ↔ 机制层）

### 4.3 与既有正典的关系（rev2）

- **接得上**：`_04.txt:137` §27 A（第一位漏洞体质者的结构位）＋ `19:12`「等级最高」、`:14`——L1 是「第一位」的自然投影；`01_苏瑾.txt:97` 的「笔·使用无限制」是同一母题在**她**身上的变奏，游戏侧兵刃是**他**身上的变奏——两条并立、互不冒充（§1.3）。

## 5. 「无限制」口径的两条写死项

### 5.1 无限制的**所指**（可证伪定义）

「无限制」在本稿里**只**指下面四件事，别的都不算：

| 维度 | 无限制的含义 | 今天的相反证据 |
|---|---|---|
| 获取 | 不需要局外货币、不需要前置、不需要第二次遇到 | `meta.gd:62` `:68` 的 cost/requires 链 |
| 上手 | 捡到即可开火，无教学、无冷却、无「先看过一次才能用」 | 现状本就如此（`player.gd:202` 只查 `DEFS.has(id)`）→ 这条**已经是事实** |
| 弹药 | 弹匣照常，但**不因「专属」而额外受限**（无耐久、无充能、无次数） | 现状无耐久概念 → 也是事实 |
| 槽位 | ⚠️ **不含**「想带几把带几把」——双槽是操作层约束，不是权限约束 | `player.gd:30` 两槽 |

🔴 **「槽位」这条是我特意划出来的**：作者说「基本上没有限制」，很容易被实现读成「扩到 4 槽」。双槽 + Q 切换是手感骨架（AGENTS §4.9 dash 区间那类实测口径都挂在它上面），**扩槽属方向级变更** → §9.2 W4（已裁：不扩）。

### 5.2 无限制**不包含**的三件事（防越界）

1. 不包含「伤害上限提高」——上限仍由 `ABYSS_TIERS` 与词缀决定（`data.gd:468-478`）。
2. 不包含「无视房型／无视灾祸」——S33 的灾祸分槽照旧生效（`game_main.gd:3955 CALAMITY_SHRINE_DOWN`）。
3. 不包含「占体质名额」——`19:45`。

### 5.3 「异常轻松」的可感知落点

不做数值膨胀，做**摩擦消失**：无购买动画、无确认框、无「首次使用时…」提示、卡片上没有锁形图标。这三条都是可截图判定的（留给 `SPR36_验证口径.md`）。

| **P-改语义**（我的建议） | 保留节点与 id，把三节点改成 `default: true`、`cost` 保留但 `requires: []`；即「节点还在，但它是一件免费拥有的收藏」 | `meta.gd:111-112` 会把它们收进 `_defaults`，`is_unlocked`（`:141-147`）直接返回 true → 零门槛；`validate.gd:512-513` 要求 cost>0 ⇒ **cost 不许改成 0**，保持 40/60/100 即可；`MIN_DEFAULT_USABLE.weapon` 由 4→7 默认可用，**阈值仍满足**；E1 **不变**（`DROP_POOL` 未动，`random_unlocked` 只看 DROP_POOL，`weapons.gd:88`） | 🟡 中：破坏「串联链」的付费曲线叙事；已购玩家在军械页会看到「已拥有 ×已购买」的重叠态，需 UI 处理 | 可：把 default 改回 false 即完全复原（存档无损） |

⚠️ **落地前必核的连锁点（本轮新实证）**：Boss 房清场那一行今天就在消费这次 rng——`game_main.gd:3005` `drop_pickup(..., "weapon", 1, _random_weapon())`，而 `_random_weapon()`（`:3030-3031`）直通 `Weapons.random_unlocked()`。T-A 把 `unlocked_ids()` 从 3 变 6 之后，凡在 Boss 房**之前**消耗 rng 的系统若其分支数依赖解锁内容，其后整条随机流都会位移。**编程侧必须在 T-A 合入当天实测三档 seed 指纹；一旦漂移，先查解锁态读取点，不许靠重定基线掩盖。**

## 7. 「一部分性能比 BOSS 还强」的死值口径

### 7.1 先把「比」的对象钉死（三问）

| 问 | 本稿的答 | 为什么必须是它 |
|---|---|---|
| **跟谁比？** | 跟**同一只 Boss 自己那一发招牌脉冲**比，不比 Boss 的 HP／防御／总输出 | Boss 的伤害出口是可数的：`boss.gd:24 var dmg := 2`、`skill_interval`（基类 `:16` = 3.0，`boss2.gd:31` = 2.2，`boss3.gd:35` = 2.6）、HP 缩放式 `boss.gd:74`／`boss2.gd:29`／`boss3.gd:33` |
| **比什么数值？** | **静态 DPS**：`dmg / interval`（`weapons.gd` DEFS 的两个现成字段），不比实战 TTK | 两字段都在表里、可读、可断言；实战 TTK 牵入命中率／词缀／暴击（`player.gd:412-413`），不可钉死 |
| **在哪个档？** | 🔴 **`abyss_tier == 0`** | 深渊乘子是纯乘算（`data.gd:468-478`），一旦掺进来「更强」会变成随档变化的模糊句；且探针 `game_main.gd:450-481` 依赖基准值不被污染（`:489` 那行构造式） |

### 7.2 可断言的定义（这就是「死值」）

```
BOSS 侧基准（每只一个常数，取自磁盘现值）：
  prism_warden     : pulse_dmg = 2 , interval = 3.0  ⇒ dps_boss = 0.667
  pyrothalassian   : pulse_dmg = 2 , interval = 2.2  ⇒ dps_boss = 0.909
  third_boss       : pulse_dmg = 2 , interval = 2.6  ⇒ dps_boss = 0.769
  （注：三只均继承 PrismWarden 的 var dmg := 2，boss2/boss3 只覆写 interval——本轮实读 boss.gd:24 / boss2.gd:31 / boss3.gd:35）

专武侧：dps_w = DEFS[id].dmg / DEFS[id].interval   （abyss_tier=0，不吃任何 buff／词缀／暴击）

「比 BOSS 强」当且仅当：dps_w >= dps_boss * R ，R := 1.25（写进 data 常量，⛔ 散写在 if 里）
```

**「一部分」到底是多大一部分**——这是设计意图，必须给数：

| 约束 | 值 | 可机检形式 |
|---|---|---|
| 每只 Boss 的专武里，满足 R 的把数 | **恰好 2 把**（4 把组）／至多 2 把（5 把组） | 遍历 `owner_boss==B` 的条目计数 == 2 |
| 不满足 R 的把数 | ≥ 其余全部，且其 `dps_w <= dps_boss`（不许「差一点就反超」的灰区） | 计数 + 不等式 |
| 全局反超比例 | 2/3 ≈ 67%（3 只 × 2 把 = 6 把可反超，共 12–15 把） | 汇总断言 |

⚠️ 三条诚实披露：
1. `R=1.25` 与「恰好 2 把」是**我提议的数**，作者可改；但**「每只 Boss 至少一把明显更弱」和「不许灰区」是我的口径底线**，因为「一部分」如果不可数就无法证伪。
2. 这个比较刻意**不含玩家侧倍率**（`damage_mult`、`bullet_dmg_mult`、暴击、词缀）——一旦含进去，「更强」在任何一档都可能被推翻，探针就失去了基准值。
3. 若作者希望「更强」体现在实战而非纸面，那就得另立一套 TTK 靶，代价是放弃死值——**这是另一个决定，不在本稿默认里**。

## 8. 红线碰撞逐条评估（AGENTS §4）

### 8.1 `meta.gd UNLOCKS` = 冻结规格 v2.10（§4.4「不可改；局外内容一律平行只读派生」）

**判定：算改规格，而且分两种程度。**

| 动作 | 是否改规格 | 程序 |
|---|---|---|
| 给三节点翻 `default: true`、清空 `requires`（§6.1 P-改语义） | 🔴 **算**——动了既有条目的字段语义 | 走「规格修订提案」：作者点头 → 编程侧改 → `validate.gd:505-543` 全跑 → 由**主理人在收官时**手工重刷 `SPR21-FROZEN.md5` 相应行 → 文档记「v2.10 → v2.11」 |
| 新增 12–15 个 `kind:"weapon"` 节点 | 🔴 **算扩表**，但符合 AGENTS §4.4 后半句「局外内容一律平行只读派生」——`UNLOCKS` 本来就是增量表（`meta.gd:7-8`「解锁关系完全由 UNLOCKS 表推导……三个池的数据表不用为解锁机制改动」） | 若走 W3-B（花钱买专武），扩表**合法且有机检兜底**（U 项 15 条门）；若走 W3-A（杀了就掉），🔴 **不建节点**才是对的——建了就把「无限制」重新变成收费 |

⚠️ 顺带发现（如实报，不擅自改）：`validate.gd:538-539` 明写「同一个内容不能被两个节点同时指向」。今天 `u_mw_cluster` 的 icon 复用 `wpn_launcher`（`meta.gd:69`）——若将来有人图省事给某把 launcher 变体再建一个 target 为 `launcher` 的节点，会被这道门当场拦下。**这不是 bug，是门在起作用**，但专武表如果按「基础武器的皮」来设计就会踩它。

### 8.2 `ACTION_DEFS` 冻结 18 个动作（§4.3）

**判定：不撞，前提是专武只用既有 7 个行为位。**

- 现有动作 18 条实数（`assets.gd:333-353`，S 项）。专武若要「BOSS 招牌动作」，注意 J 项：Boss 的招牌技本来就是**复用既有实体**（毒云／藤蔓／击退／减速／落钻），玩家侧对应物就是 `bullet.gd:25-28` 那 7 个参位（L 项）。
- ✅ 正确做法：**只做数据组合**（`dmg/interval/count/spread/speed/mag/reload/pierce/life/explosive` + `homing/arc/cluster`）。
- ⛔ 禁止：为新武器加第 19 个 action（例如「专属技能键」）。那需要 `ACTION_DEFS` 扩 + 按键重绑 + 设置页，属方向级变更。
- 🔴 硬前置：K 项那条自测（`game_main.gd:2569-2570`）**把数量 3 当前提**。新增带行为位的武器而不更新它，它照样绿——**假绿**。落地时必须把它改成「遍历所有 DEFS 中带任一行为位的条目」，并为它配一条变异刀（故意把一个 `arc` 写错，断言必须红）。

### 8.3 图鉴分母／白名单（`validate.gd:255-257`、`menu.gd:488/492`、`game_state.gd:296-320`）

**判定：只要不新增 kind，就一处都不带动；但要主动决定「专武要不要进图鉴」。**

- 现状：**武器根本不是图鉴类别**。`codex` 只有 6 类（`game_state.gd:282` enemies/relics/suffixes/themes/bosses/shrine），`_codex_id_valid`（`:296-320`）没有 weapon 分支，FLAVOR 也没有 `weapons/` 前缀（`grep '"weapons/' data.gd` 零命中）。
- ⇒ 因此「加 12–15 把武器」**不会**连带动 `CODEX_*` 分母（R 项全是表长派生，与武器无关）。
- 🔴 但如果选择让专武进图鉴（我建议进，否则「收集」没有可见反馈，违反登记三件套第③条「可见效果断言」），那就是**新增第七类 kind**，牵动：`game_state.gd:282` 初始化两处、`_codex_id_valid`、`menu.gd` 分母节、`validate.gd:250-260` FLAVOR 覆盖门（要补 `weapons/*` 手记，缺一条即「表不齐」）、以及存档兼容（旧档 `codex` 无该键 → 需 `.get` 兜底）。这是一整个微批，不能顺手做。
- ⛔ 红线照守：**`CODEX_BOONS[*].kind != suffixes`**（`validate.gd:264-272`）与 **`!= shrine`**（`:273-278`）。若将来给专武设「集齐 N 把」的 boon，kind 用 `weapons` 没问题，但**绝不允许**把 `suffixes` 或 `shrine` 拿来当阈值。

### 8.4 出卡池：`SHRINE_OFFERS`（`data.gd:313`）与 `FLOOR_POOLS`（`data.gd:90`）

**判定：`FLOOR_POOLS` 完全不相关（它是刷怪池，`validate.gd:113-120` 只校验敌人 id）；圣所侧不许动结构。**

- 🔴 `_shrine_theme_pref()` 的 `[up, down]` 两段结构**不许动**（`game_main.gd:3940-3950`，8 条 rule 各返一对数组）。专武**不进圣所池**——圣所卖的是「状态交换」，卖武器会把它变成商店，与 S13 A「纯 swap 零赌局」的定位（`data.gd:310-312` 注释）冲突。
- 若作者坚持要一条「圣所给一把专武」的选项，那是**新增 SHRINE_OFFERS 条目**，牵动 `validate.gd:257`（FLAVOR shrine 分母）+ `menu.gd:492`（第六类分母）+ `game_state.gd:317-319` 白名单 + `CALAMITY_SHRINE_DOWN`（`:3955-3960`）是否要为它加一条压低项。**成本远大于收益，本批不做**（§10）。
- 真正的出卡路径是 `game_main.gd:3005`（Boss 房）／`:3236`（商店）／`pickup.gd:154`（大宝箱），三者都调 `random_unlocked()`（P 项）→ 改动集中在**这一个入口**，见 §6.2 α 路的零 rng 要求。

### 8.5 美术队列：12–15 个新图标／贴图

**判定：AI 出图这条路进不了这批，必须按 AGENTS §9.3 的程序化路线写。**
