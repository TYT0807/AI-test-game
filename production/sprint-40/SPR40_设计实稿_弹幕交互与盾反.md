## 0. 结论先行

1. **「非激光类型的漂浮子弹」在今天的代码里有一个零新字段的精确解**：敌弹全部由唯一入口 `Game.main.spawn_enemy_bullet()` 生成，该入口只给 `pierce=0 / explosive=0 / bounce=0 / frost=0 / homing=false / arc=0 / cluster=0`（实读：函数体一行 `b.setup(pos, dir, speed, dmg, false, tint, 0.85, 0)`）。⇒ **分类判据＝「`friendly==false` 且七个行为位全为零」**。今天这条判据对全体现存敌弹恒为真（等价于「全是漂浮弹」），将来一旦有激光／束流／裂变型敌弹，它自动把它们排除在外——**这就是可现读的分类，不需要给 `bullet.gd` 加字段**（第 8 参位被占用的红线因此根本不触碰）。
2. **近战清弹必须挂在 `_swing()` 已有的那条敌人扫描循环之后，作为第二条独立扫描**，⛔ 新开 Area2D、⛔ 新碰撞层/掩码（HP-5 同源约束：会与 `bullet.gd` 的 layer 8/mask 1|4|64 打架）。几何复用同一个 `reach` 与 `arc_deg`，所以玩家感知是「这一刀的刃风把弹扫掉了」，不会出现「挥到怪却扫不到身边的弹」这种割裂。
3. **🔴 rng 红线的绕法不是「省一次抽取」，而是「换一条随机流」**。E1 契约管的是 `Game.rng` 这条**主叙事流**的位置；项目早就有一条专供表现层的旁路 `Game.fx_rng`（`game_state.gd:41`，播种 `hash("spr8_fx:%d" % run_seed)`，`reset_fx_rng()` 随局重置），音效抖动今天就走它。**裁定：清弹与盾反的全部随机性一律走 `fx_rng` 或纯确定性算术，`Game.rng` 消费恒为 0。** 于是「每次有效挥击恒 1 次 `Game.rng.randf()`」这条硬约束**逐字不动**，V-E1d 那两把刀继续有效。（⚠️ 附带发现见 §6：`bullet.gd:_split_cluster()` 今天在主流上抽 3 次，与本红线精神冲突，另案。）
4. **盾反不做成「第三把武器」，做成 `shieldbash` 形态自带的一层窗口**。S38 已经把 `sh_bulwark` 定成 `kind:"shieldbash"`（`arc_deg=150` 全场最宽、`interval=0.90` 最慢、`dmg=1.20`），这三个数天然就是「举盾」的手感骨架。⇒ **⛔ 新增 action**（`ACTION_DEFS` 18 条不动）：架式＝当前武器是 shieldbash 形态且刚挥出（B2a 的 `_stance_t` 窗口还开着）时自动进入。玩家学到的是「按同一键，但要在弹到达前按」，而不是「多一个键」。
5. **眩晕（`stun`）是新控制态，必须与既有减速正交且默认不影响伤害管线**。现有唯一同类是 `apply_slow(mult, dur)`（`slug.gd:130`、`boss.gd:323`、`player.gd:798`）。裁定：新增 `Slug.apply_stun(dur)`，语义＝AI 停摆＋位移归零，⛔ 改 `take_damage` 签名、⛔ 让受击判定变化、⛔ 对 Boss 生效（Boss 免疫，见 §3 表末行）。是否给敌人新增「眩晕」词缀属方向级 ⇒ §7 C3。
6. **本批只做「盾反成功 → 返还物」这一条最小闭环**，⛔ 一次性铺开六类攻击 × 六种返还。返还表先立**类型口径**（表在 §4），实现按 §7 的裁定分档投喂。

## 2. (a) 近战清理漂浮弹幕

### 2.1 分类判据（可用现有字段现读，我裁）

```
可被近战清理  ⟺  is_instance_valid(b)
              ∧ b.friendly == false                    # 只吃敌弹，⛔ 把自己发的弹扫了
              ∧ b.pierce == 0 ∧ b.explosive == 0.0 ∧ b.bounce == 0 ∧ b.frost == 0.0
              ∧ b.homing == false ∧ b.arc == 0 ∧ b.cluster == 0
```

- 前半是「敌弹」，后半七项是「**漂浮弹**」——七个行为位任一非零意味着这发弹携带机制（穿甲／爆炸／弹墙／冰冻／追踪／连锁／裂变），那就是「不属于可被刃风扫掉的死物」，正是作者说的「非激光类型」这一类对立面的技术表达。
- 🔴 判据必须是**一个函数**（建议 `Bullet.is_sweepable() -> bool`，纯 getter，⛔ 副作用、⛔ 读私有 `_life`），生产侧与探针 oracle **共用这一份**。理由：S33 那次「净化门槛那行复制了 3 份、探针假绿」的教训——过滤条件散写＝改了实现忘了改 oracle。
- 现状核对（G1/G2）：现存敌弹**全部满足**该判据 ⇒ 上线当天「能扫掉一切敌弹」，这是**符合预期的基线**，不是 bug。它的意义是给未来的激光/束流敌弹预留一条自动豁免通道。

### 2.2 清理的结果形态：删除 ＋ 就地迸星，⛔ 转化友方弹（我裁）

三选一里我选**删除**，另两项的理由也如实写出来：

| 方案 | 判定 | 理由 |
|---|---|---|
| ① 删除＋粒子 | ✅ **采用** | 与 G5 环盾先例同构（`queue_free()` ＋ 视觉反馈），零新实体、零 rng、零持久状态；玩家读到的是「刃风扫出一片火星」，干净 |
| ② 转为无害粒子继续存在 | ⛔ | 「无害粒子」若仍是实体就要走 `entities`，多一类需要生命周期管理的节点，收益为零 |
| ③ 转化为友方弹（反弹） | ⛔ **本批不做**，列 §7 A2 | 看着最爽，但它是**新的伤害出口**：反弹弹要打谁、伤害怎么算、要不要抽 crit（一抽就动主流），并且和本文 §4 的盾反返还**功能重叠**。若两处都能反弹，玩家分不清「哪个才是我的输出手段」。⇒ 反弹这件事**只属于盾反**，近战清弹专职防守。这是一条排他裁定，防的是两条系统互相稀释。 |

**衔接格挡**：不清弹→格挡的因果链（那是盾的事），但**允许同一次挥击既扫弹又打人**（G6 的敌人扫描在前、弹扫描在后，互不阻断）。⛔ 「扫到弹就取消本次伤害判定」——那会让玩家在混战里不敢用近战清弹。

### 2.3 rng 红线的绕法（关键条款）

🔴 **禁止形态**（三种都会漂指纹，别试）：
- 在 `_swing()` 里为清弹**再抽一次** `Game.rng.randf()`（哪怕只在「扫到了」的分支里）⇒ 变成「扫到抽 2 次、没扫到抽 1 次」＝命中相关的抽取，正是 HP-3 禁的第③条的字面形态。
- 把已有的那次抽取改成「先判有没有弹再决定抽不抽」⇒ 空挥少抽 1 次＝往前挪一格。
- 用 `Game.rng` 决定迸星颜色/角度 ⇒ 同上。

✅ **允许形态（裁定口径）**：
1. `Game.rng` 消费**恒为 0**（相对改前）：清弹逻辑一行都不碰主流。
2. 需要随机观感时用 `Game.fx_rng`（G9），或干脆用**确定性映射**——迸星角度取 `b.vel.angle() + PI`（沿来路炸开），无随机。我倾向后者：确定性的东西好写断言。
3. 计数守恒的可观测形式：`Player.melee_rng_draws == Player.melee_swings` 在开启清弹后仍逐字成立（G6 已有这两个计数器与 V-E1d 两把刀，**不需要新计数器就能机检这条**）。

### 2.4 边界态（验收要覆盖，别只测顺风）

| 态 | 期望 |
|---|---|
| 配额见底（`mag()<=0`）走进 `_start_reload()` 早退 | ⛔ 扫到任何弹（早退发生在扫描之前，天然满足；但要断言「重载那一拍零清除」，否则会出现「空挥也能清场」的白嫖） |
| 过载中（`skill_active()`） | 照常清理（与近战伤害同权） |
| 一帧内多颗弹在同一扇区 | 全部清理，`cleared` 计数＝颗数（探针据此复算） |
| 携带行为位的敌弹（探针须手工造一颗 `explosive>0` 的假弹） | ⛔ 被清理，且⛔ 被误计入 cleared |
| 已 `queue_free()` 但未出树 | `is_instance_valid` 挡住，⛔ 二次计数 |
| 友方弹恰好在扇区内 | ⛔ 被清理（`friendly` 判据） |
| autopilot（E3 路径） | 与手动同权（清弹不看输入来源） |
| 词缀触发 | 环盾用的是 `ON_SHIELD_BREAK`；近战清弹**不复用**那个 trigger（否则「凝滞矢/霜爆」这类挂环盾的词缀会被近战白嫖）。若无对应 trigger，本批**不触发任何词缀**，列为已知缺口 ⇒ §7 A3 |

## 3. (b) 盾与盾反：总体结构

### 3.1 三层窗口（我裁的结构，数值待裁）

```
举盾（RAISE）    ：当前武器 kind == "shieldbash" 且 _stance_t > 0        → 持续态，无独立计时
盾反窗口（PARRY）：进入架式后的前 W_parry 秒                              → 窄窗，成功则走返还表
硬格窗口（BLOCK）：举盾但未在盾反窗口内                                   → 宽窗，减伤不免伤，无返还
```

- 🔴 三个量全部用 `Game.FIXED_DT` 递减（G8），⛔ raw delta、⛔ `Engine.time_scale`、⛔ `get_tree().create_timer()`（后者在冒烟 2× 下与 FIXED_DT 不同步，是本仓反复踩过的口径分裂）。
- 为什么复用 `_stance_t` 而不新起一个窗口变量：B2a 已经保证了「窗口内动画不被切走」，也就是说**架式窗口就是这面盾举着的那段时间**；再起一个并行计时必然出现「一个还开着、一个已关」的双账（S38 记录过 `_sp_hold_t` 与 `_stance_t` 必须各记各的账是因为**探针不能与实现共用变量**——那是探针侧的独立性要求，⛔ 反过来理解成实现也该有两套窗口）。
- ⚠️ 已知粗糙处如实报：`_stance_t = maxf(_attack_anim_len(), _interval())`（G7），而 `sh_bulwark.interval=0.90`、attack 动画实测 0.3333 ⇒ 窗口长度目前由 **interval 主导（0.90s）**。这意味着「举盾后前 W_parry 秒」里的 W_parry 是从一次挥盾的**起手**算起，而 `W_parry ≪ 0.90`。手感上等价于「挥盾的瞬间有一小段完美帧」，这与《只狼》的「弹开」不同、更接近「抓 incoming 的时机按下盾」。是否要把完美窗口改成「按下后延迟开启」或「跨两次挥盾共享」属手感题 ⇒ **§7 C1 待裁**，本文口径先按「起手即开窗」实现，因为它零新计时、可证伪性最好。

### 3.2 判定与结算次序（🔴 顺序即口径）

敌弹命中玩家的现行路径是 `Bullet._handle_hit()` → `body.is_in_group("player")` → `take_damage(...)`（G11）。裁定插入点与优先级：

```
1) 弹仍在飞 → 每物理拍，处于 RAISE 的玩家扫描 enemy_bullets 组
   （手法照抄 G5：遍历组、distance_to < R_shield、is_instance_valid）
2) 命中距离内：
   a. 若在 PARRY 窗口 → 走 §4 返还表；弹被消耗；不结算伤害；parry_count += 1
   b. 否则若在 BLOCK 窗口 → 伤害乘 BLOCK_MULT（减免但不免）；弹被消耗；block_count += 1
   c. 否则 → 原样 take_damage（⛔ 改动现行受伤路径的任何其它分支）
3) 与 relic_shield_t 的关系：环盾豁免优先（G11 的 return 在最前），
   两者同时生效时按「环盾吃掉这颗弹」计，⛔ 既算盾反又算环盾摧毁（双计＝白嫖两套词缀）
```

- 🔴 **a/b/c 三分支必须各自有独立计数**，且返还表的每一类都要能被探针单独构造（见 `SPR40_验证口径.md` V-P3）。历史教训：只有总数没有分类计数的断言，永远查不出「所有攻击都返同一种东西」这种偷懒实现。
- ⛔ 修改 `Bullet.setup()` 的参数位（第 8 参位占用红线）；⛔ 给 Bullet 加持久字段来标记「已被盾反处理」（用一个 `_parried` 布尔也算新增状态，除非必要——首选「处理完立刻 `queue_free()` ＋ 由玩家侧计数」，与 G5 同构）。

### 3.3 眩晕（stun）口径

- 新增 `Slug.apply_stun(dur: float)`：置 `_stun_t`，`_stun_t > 0` 期间 AI 决策不推进、`velocity` 归零（沿用既有 `_knock` 衰减写法之外的最保守做法：**只冻结主动位移**，⛔ 冻结 `_knock`，否则与 dash 位移区间纠缠那条禁令撞车）。
- 计时走 `Game.FIXED_DT`（G8）。
- ⛔ 影响受伤公式、⛔ 增伤、⛔ 改 `take_damage` 签名（G6 里 spear 破甲那条「本帧旁路标志」的教训：任何跨帧残留的临时标志都会泄漏到子弹路径）。

## 6. 顺带发现的口径隐患（如实报，不擅自改）

1. **`bullet.gd:_split_cluster()` 在主叙事流上抽 3 次**（`Game.rng.randf() * 0.4` 在 `for i in 3` 里）。这与「抽取次数应与玩法事件解耦」的精神冲突：携带 `mw_cluster` 与否、以及打没打到，都会移动主流位置。它不是本批引入的，也可能已经是既定事实（冻结串在有无 cluster 的两条路径上分别采过），但请编程侧**实测一次**：同一 seed 下，`mw_cluster` 命中 vs 未命中，其后续 `[SMOKE-META] fingerprint` 是否漂移。若漂移，这是比盾反更值得先修的确定性缺陷 ⇒ 交我裁定，⛔ 自行改。
2. **`_fire()` 在 `n==1` 且非 autopilot 时额外抽一次 `randf_range(-1.5,1.5)`**（G/F12）。⇒ 单发武器的抽取是「1 次抖动 ＋ n 次 crit」，霰射是「n 次 crit 无抖动」。这不违反「恒 1 次」那条（那是**近战**的口径），但意味着**弹幕侧的抽取次数本来就随 count 变化**，写盾反返还断言时⛔ 拿「返还了几发弹」去推「应该抽几次」——正确做法是直接锁 `Game.rng.state` 不变（§4.2 末）。
3. **`validate.gd` 的 dps 门是「一律从 `Weapons.DEFS` 与 `Data.BOSS_PULSE_BASE` 现算」**（`:416`）。若盾反返还借用 DEFS 模板（我裁定如此），这条门的分母会多出「返还弹」这一类伤害出口 ⇒ 需确认它只统计玩家主动开火路径，⛔ 被返还弹污染。请编程侧在 S40-c 开工前先跑一次该门并贴出现算式。
