### 0.1 两个函数的实施规格（⑯ 的靶子，请照抄）—— **已采纳、必装**

> 本节与实施单 **§2.3 / §2.4** 同规格；**不是可选改进**。判据：不装这一层，「`pair.x`/`pair.y` 接反」就只能靠 ⑨ 的 1/6 抽签撞见（见 §3.8 采纳理由）。

**函数一 · 映射表**（6 行）：

```gdscript
	# 纯函数：modifier → (enemy_speed_mult, diamond_mult)。零 rng、零副作用、不读成员。
func _modifier_mult_pair(m: String) -> Vector2:
	match m:
		"rage":   return Vector2(1.25, 1.0)
		"barren": return Vector2(1.0, 0.7)
		"swarm":  return Vector2(1.0, 1.5)
		_:        return Vector2(1.0, 1.0)
```

**函数二 · 接线**（7 行，**这一层是 ⑯ 主靶**）：

```gdscript
	# 纯函数：把映射结果同时写进 _mod_* 与 live 四字段。零 rng、零副作用（只写这四个倍率）。
func _apply_modifier_mult(m: String) -> void:
	var pair := _modifier_mult_pair(m)
	_mod_enemy_speed_mult = pair.x
	_mod_diamond_mult = pair.y
	enemy_speed_mult = _mod_enemy_speed_mult    # live 只从 _mod_* 读，不留第二个可写来源
	diamond_mult = _mod_diamond_mult
```

`_roll_modifier()`（`:1206`）里**只加一行调用、并删掉 `match` 里的三处倍率赋值**，其余一个字不动：

```gdscript
	# 插在 :1213 之后、match 之前
	_apply_modifier_mult(modifier)
```

🔴 **`match` 里必须删掉的三行**（不是"可以删"，是**必须删**）：
- `:1216` `enemy_speed_mult = 1.25`（rage）
- `:1219` `diamond_mult = 0.7`（barren）
- `:1229` `diamond_mult = 1.5`（swarm）

**为什么必须删**：留着这三行，倍率就**有两个来源**——函数一个、match 字面量一个。两者今天数值相同，所以测试全绿；但任何一次只改一边（改映射表忘改字面量，或反过来）都会让 `_mod_*` 与 live 值分叉，而 `_apply_floor_theme()` 下次复位时会把 live 拉回 `_mod_*`，**于是"本局看起来生效、离压后突然变回另一个值"**——这正是 C1 想消灭的那类 bug 换了个位置复现。删掉之后倍率**唯一来源是函数返回值**，"忘双写"才在结构上不可能发生。

> **为什么拆成两个函数而不是一个**：`_modifier_mult_pair()` 只回答"映射对不对"，`_apply_modifier_mult()` 还回答"有没有接对分量"。**⑯ 必须调第二个**——调第一个只能验映射表，`pair.x`/`pair.y` 接反它完全看不见（编译不报、运行不崩，只让两个倍率互换）。拆开之后探针能分别打靶，而且第二个函数是零副作用的，调它不会污染任何东西。

**diff 形状（供核验方核对：**新增 2 个函数（6 + 7 行）+ 1 行调用 + 3 行删除**）**：
```
+ func _modifier_mult_pair(m: String) -> Vector2:   # 6 行
+ func _apply_modifier_mult(m: String) -> void:     # 7 行
+ 	_apply_modifier_mult(modifier)                  # 插在 :1213 后
- 	enemy_speed_mult = 1.25      # :1216
- 	diamond_mult = 0.7           # :1219
- 	diamond_mult = 1.5           # :1229
```
⚠️ **若实施方选择"保留 match 三行"**：不违规，但必须在交付说明里写明，且**核验侧要把 ⑯ 与 ⑨ 的结论合并读**（⑯ 绿只说明函数对，live 值仍可能被字面量覆盖）——**"单一来源"这个结构保证不成立，C1 的回潮风险回到人工评审**。默认方案是删。

🔴 **探针调用纪律（红线范围内的例外要写清）**：探针**可以**直接调 `_modifier_mult_pair()` 与 `_apply_modifier_mult()`——两者零 rng、零外部副作用；探针**仍然禁止**调 `_roll_modifier()`（它走 `Data.roll_modifier()` → `Game.rng.randi_range`，会破 ⑤5 的 `Game.rng.state` 断言）。调 `_apply_modifier_mult()` 会写四个倍率字段，**必须进出口还原块**。

**modifier 全集实读**（`data.gd:271-278`，共 6 个，无第 7 个）：`none / rage / barren / overload / glass / swarm`；权重 `MODIFIER_WEIGHTS`（`:279`）`none=4`、其余各 2 → **`none` 是最高频一档，也最容易在 match 里掉进默认分支而无人发现**，所以 ⑯ 必须显式验它。

| modifier | `enemy_speed_mult` / `_mod_enemy_speed_mult` | `diamond_mult` / `_mod_diamond_mult` | 走哪个分支 |
|---|---|---|---|
| `rage` | **1.25** | **1.0** | 显式 arm |
| `barren` | **1.0** | **0.7** | 显式 arm |
| `swarm` | **1.0** | **1.5** | 显式 arm |
| `overload` / `glass` / `none` | 1.0 | 1.0 | `_` 默认分支 |

> 🔴 **读这张表时注意列**：`rage` 是唯一让**敌速**变化的（1.25）；`barren` / `swarm` 都只动**残响**。⑯ 的四条期望就是照这张表抄的，**任何一条把两列读反都会在正确实现上必红**。

🔴 **以下副作用全部留在 `_roll_modifier()` 原位，禁止搬进任何一个函数**——两个函数只管那两个倍率，多收一样就把 `_roll_modifier()` 的副作用面也搬进来了，属于扩大改动面：
- `rage` → `enemy_hp_mult = 0.85`（`:1217`）
- `barren` → `Game.add_diamonds(10)`（`:1220`）
- `overload` → `player.skill_cd_mult = 0.6` / `player.max_hp = maxi(1, player.max_hp - 1)` / hp 夹取（`:1222-1224`）
- `glass` → `player.crit_chance` / `player.speed_base *= 0.9`（`:1226-1227`）

> ⑯ 之所以能验到映射与接线，前提就是**两个函数都无副作用可观测**：只写四个倍率字段、不碰 `player`、不碰 `Game`、不消耗 rng。所以探针调它们**不会**破 ⑤5。

### 1.3 🔴 一处必须纠正的判定前提：`⑥4` 不是"唯一一条把 bug 写进期望值的绿"

## 二 覆盖缺口：只改期望值，④ 与 ⑥4 会变瞎

> 🔴 **这是本批最容易漏的一手。** 改完 C1，`:815`/`:1053` 断言点的上游多了一条 `_apply_floor_theme()` → 无条件把 `diamond_mult` 复位成 `_mod_diamond_mult`（1.0）。于是**无论 clear 有没有正确还原 1.5，末值都是 1.0**——断言照绿。批一里 ④/⑥4 之所以能抓「clear 里现查新层主题」（变异 D），靠的正是那个 1.5 的观测。直接改成 1.0 = 把变异 D 的靶子拆了。

**补法（新增 2 条，不动原有 2 条）**：在 `_ct_floor_advance()` 之后、`_calamity = ""` + `_apply_floor_theme()` **之前**插一条读数——此时 `_calamity` 仍是旧值、clear 刚跑完、主题还没换，`diamond_mult` 必须是 **1.5**。

| 新增 | 位置 | 断言 | 期望 |
|---|---|---|---|
| ⑮1 | ④ ore@pressure 段，`_ct_floor_advance(7)` 之后 | `diamond_mult == 1.5`（clear 还原 saved） | 1.5 |
| ⑮2 | ⑥4 段，`_ct_floor_advance(7)` 之后（与 ⑥2 同一位置，⑥2 读字符串、⑮2 读数） | `diamond_mult == 1.5` | 1.5 |

这样一对断言把两件事分开锁死：**⑮ 锁「clear 还原对不对」（陷阱 1 的靶子）**，改后的 `:815`/`:1053` 锁「离压后主题复位对不对」（C1 的靶子）。两者缺一，就有一半的失败面没人看。

**注**：⑥2（`_calamity_theme_rule == ""`）已经在这个位置，但它验的是**字符串标志**，不验数值——它抓不到"快照清空正确、但还原值算错"。⑮2 补的就是数值面。

### 2.1 🔴 ④ / ⑥4 段必须先把 `_mod_*` 归一到 1.0，否则新期望是一个**不确定值**

这条不讲清楚，`:815`/`:1053` 改成 1.0 会变成**~29% 概率误红的 flaky 门**，比不改更糟。

**为什么**：C1 之后，`_apply_floor_theme()` 在无 pressure 分支的层（第 7 层 silent）把 `diamond_mult` 复位成 **`_mod_diamond_mult`**，**不是 1.0**。而 `_mod_diamond_mult` 的值取决于**本局真实抽到的 modifier**：

| 本局 modifier | `_mod_diamond_mult` | 第 7 层复位后 `diamond_mult` |
|---|---|---|
| `none` / `overload` / `glass`（权重 4+2+2 = 8/14） | 1.0 | **1.0** |
| `barren`（2/14） | 0.7 | **0.7** |
| `swarm`（2/14） | 1.5 | **1.5** |

**结论**：把期望写死 1.0，在 `barren`（14.3%）与 `swarm`（14.3%）两局里**会红在正确实现上**——合计约 **28.6%**。这种红最难查：换 seed 重跑就绿，核验方会误判成"探针不稳定"。

**规定做法**（与 ⑧ 完全同一套，别自创）：
1. 进入 ④ 段 / ⑥4 段**之前**，把 `_mod_enemy_speed_mult = 1.0`、`_mod_diamond_mult = 1.0` 显式置位（覆盖本局真实值）。
2. 段内所有期望按 `_mod_* = 1.0` 写死（`:815`/`:1053` 写 **1.0**）。
3. **出口还原块**（`:1181` 起）从探针**入口快照**恢复这两个字段——**不许还原成 1.0**（那会污染本局真实 modifier，属于静默改状态）。§五 第 7 条就是这个意思。
4. 归一化必须是**段级**的，不许在 ④ 段中间改一次、⑥4 段又假设它还是 1.0——两段各自归一，互不依赖执行顺序。

> **⑮ 不受此影响**，可以放心写死 1.5：`pressure` 的 `maxf(_mod_diamond_mult, 1.5)` 在 `_mod_diamond_mult ≤ 1.5` 时**恒等于 1.5**（swarm 的 1.5 也一样），所以 `saved` 恒为 1.5，clear 还原恒为 1.5。**这是唯一一处"写死数值仍然安全"的地方，理由要记住：maxf 把 modifier 的影响吃掉了。**
>
> ⑦（`:1106` 的 −53%）同理安全：`minf(1.5, 0.7) = 0.7`、`saved = 1.5`，`(1 - 0.7/1.5) = 53%`，与本局 modifier 无关。

**归一化范围要收住，别全局铺开**（铺开会牵动批一已成立的断言）：

| 段 | 要不要归一 `_mod_*` | 理由 |
|---|---|---|
| ④ 段（`:815` 那条及其上游） | **要** | 第 7 层复位出的是 `_mod_diamond_mult`，不归一则期望不确定 |
| ⑥4 段（`:1053`） | **要** | 同上 |
| **④c 的 13 号格**（pressure×scarce_ore 扫描） | **不要** | 三步读数全部被 `maxf` 掩蔽（1.5 / `minf(1.5,0.7)=0.7` / 还原 1.5），与本局 modifier 无关；强行归一只是白改 |
| ⑧ / ⑩ / ⑪ | **要**（本来就是构造的一部分） | 它们必须精确控制 `_mod_*` 才能验"贡献有没有被抹掉" |
| ①–③ / ⑤ / ⑦ | **不要** | 不读这两个字段，归一反而扩大状态改动面 |

> 一句话：**只有"读数落在无 pressure 分支的层上、且读的是 `diamond_mult`/`enemy_speed_mult`"的地方才需要归一。** 其它地方要么被 maxf 掩蔽、要么根本不读这两个值。

### 3.2 ⑨ `_mod_*` 接线巡检（1 条，⚠️ 只验标志）

| 错误形态 | 谁抓 |
|---|---|
| 映射表写错（`rage` 映射成 `(1.0,1.0)`） | **⑯1-⑯4**（确定性，6 档全覆盖） |

### 3.3 ⑩ modifier × pressure（3 条）——⚠️ 只抓「改成乘法」

| 构造 | 期望 | 只抓什么 |

| `_mod_diamond_mult=0.7`（barren）+ pressure | `diamond_mult == 1.5` | 乘法会得 0.7×1.5=1.05 → 红 |
| `_mod_diamond_mult=1.5`（swarm）+ pressure | `diamond_mult == 1.5` | 乘法会得 2.25 → 红 |

> 🔴 **必须写明这三条抓不到什么**：`maxf` 会掩蔽。漏写 `_mod_*` 时字段恒 1.0，`maxf(1.0,1.3)=1.3`、`maxf(1.0,1.5)=1.5`——**与写对时逐值相同**。所以这 3 条 **不能** 当作「modifier 贡献没被抹掉」的证据，它们只证明"没把 maxf 换成乘法"。真靶子在 ⑪。

> **一句话定级（核验方引用这句即可）：⑩ 只对「把 maxf 改成乘法」这一种错误有效，对其余任何 C1 错法均无效。** 统计有效覆盖时按 0 条计、或单列"乘法回归"一类，**不许并入 C1 正面证据**。

### 3.6 ⑬ C2 四条速度路径（4 条，验效果型）

| ⑬1 | defuser 冲向炸弹（`:216`） | `s.defuser = true`；`BombScript.new()` 加入 `"bombs"` 组、置于 ~100px（**不许 <18px**，否则触发 `defuse()`） | `s.velocity.length()` |

### 3.8 ⑯ modifier 映射 + 接线覆盖（4 条，验效果型）—— 调 `_apply_modifier_mult()` 后读 live，6 档全覆盖

> **状态：已采纳、必装，不是可选项。** 权威规格见实施单 **§2.3**（新增 `_apply_modifier_mult(m)`：四行赋值、零 rng、零副作用）、**§2.4**（`_roll_modifier()` 只留一行 `_apply_modifier_mult(modifier)` + 删 `match` 三行）、**§5.2**（⑯ 改读 live 两值、同一 `and` 链连断 `_mod_*`）、**§6.2 刀 G**。本节与实施单口径一致；有出入以实施单为准。
>
> **采纳理由（要点：不是为了多一个函数）**：原方案下 ⑯ 只调映射函数，「`pair.x`/`pair.y` 接反」这个失败面**只能靠 ⑨ 的 1/6 抽签撞见**。而这类错误**编译不报、运行不崩，只让两个倍率互换**——是最像"一切正常"的一类错，也是最容易上线后几周才被玩家发现的。抽出接线函数之后它变成**确定性红（刀 G）**，代价只有 7 行。

**构造**：`_apply_modifier_mult(<modifier>)`（零 rng、只写四个倍率字段）→ **读 live 两值 + `_mod_*` 两值**，一条断言内一起断。
**不碰** `player`/`Game`/rng，所以**不属于** §五 第 3 条红线（禁的是 `_roll_modifier()`）。会写四个倍率字段 → **必须进出口还原块**。

| # | 入参 | `enemy_speed_mult` 与 `_mod_enemy_speed_mult` | `diamond_mult` 与 `_mod_diamond_mult` | 抓什么 |
|---|---|---|---|---|
| ⑯1 | `"rage"` | **1.25** | **1.0** | 映射写成 `(1,1)`；或 1.25 接到 diamond；或 `pair.x`/`pair.y` 接反 → 红 |
| ⑯2 | `"barren"` | **1.0** | **0.7** | 0.7 接到 enemy_speed → 红 |
| ⑯3 | `"swarm"` | **1.0** | **1.5** | 1.5 接到 enemy_speed → 红 |
| ⑯4 | `"none"` / `"overload"` / `"glass"` **逐个过一遍**（1 条聚合） | 1.0 | 1.0 | 默认分支被写成非 1.0（如复制粘贴 rage 的 arm）→ 红；漏 arm 掉进默认分支仍得 1.0 → **不红** |

> 🔴 **读表注意列**：`rage` 是唯一动**敌速**的（1.25）；`barren`/`swarm` 都只动**残响**。⑯3 的期望是 **敌速 1.0 / 残响 1.5**，写成"1.5 / 1.0"会在**正确实现上必红**，且形状与 ⑯1 一模一样（复制粘贴痕迹）。**这一条按代码写（`:1216` 只有 rage 写 `enemy_speed_mult`；`:1228-1229` swarm 写的是 `diamond_mult`），不按任何口头口径。**

🔴 **每条的写法：一条断言、四个值、同一个 `and` 链，不许拆。**
```gdscript
_apply_modifier_mult("rage")
_ct_assert(is_equal_approx(enemy_speed_mult, 1.25) and is_equal_approx(_mod_enemy_speed_mult, 1.25)
		and is_equal_approx(diamond_mult, 1.0) and is_equal_approx(_mod_diamond_mult, 1.0),
	"⑯1 rage 映射+接线 (敌速,残响)", "%.2f/%.2f" % [enemy_speed_mult, diamond_mult], "1.25/1.00")
```
三处理由：① **拆成两条会让 `declared` 从 103 变 107**；② **只断一个值，接反有一半概率蒙对**（rage 断敌速抓住、断残响抓不住），合进一个 `and` 则接反必红；③ **同时断 live 与 `_mod_*`，是为了抓"只写了一边"**——只断 live 的话，"live 写对、`_mod_*` 没写"会全绿，而那恰好就是 C1 会在离压后爆出来的形态。失败信息里 two measured 都要打，否则看到 `measured=1.00` 分不清是哪个分量错。

**⑯4 的内部读数用扫描前缀**（不得用 `#NN`，见 §五 第 2 条）：
```
[SMOKE-CAL-THEME] pair m=%s got=(%.2f,%.2f) mod=(%.2f,%.2f)
```
> **为什么 ⑯ 必需、⑨ 替代不了它**：⑨ 每局只看得见当前抽中的那 1 个 modifier，⑯ 一次覆盖全部 6 档且不依赖随机。这是"6 个 modifier 只覆盖 1 个"这个缺口的正解，也是把 `declared` 从 99 抬到 103 的唯一理由。

🔴 **⑯ 现在覆盖什么、还漏什么**（采纳 `_apply_modifier_mult()` 之后的最终版）：

| 错误形态 | ⑯ 抓得到? | 谁抓 |
|---|---|---|
| 映射表写错（`rage` 返回 `(1.0,1.0)`） | ✅ **确定性红** | ⑯1 |
| **`pair.x`/`pair.y` 接反、或同一分量写两遍** | ✅ **确定性红**（读 live 值） | ⑯1 / ⑯2 / ⑯3 |
| **live 写了、`_mod_*` 没写**（反之亦然） | ✅ **确定性红**（一条断言里两边都断） | ⑯1-⑯4 |
| **`_roll_modifier()` 根本没调 `_apply_modifier_mult()`** | ❌ **红不了**——⑯ 是直接调函数的，绕过调用点 | **只有 ⑨** |

> **也就是说：⑯ 把「函数本身对不对」整片吃掉了，只剩「有没有被调用」这一层留给 ⑨。** 这个边界是这次拆两个函数换来的，写在这里免得后人拿 ⑯ 的绿去证明"生产路径跑通了"——**它证明不了**。

> **实现漂移容忍**：若实施方把函数命名成别的（`_mod_pair` / `_modifier_mult` / `_apply_mod`）或加 `static`，**名字以实施单为准**，本文只约束四件事：① 映射函数签名 `String → Vector2` 返回 `(敌速, 残响)`；② 接线函数接收 modifier 并写四个倍率字段；③ 两者零 rng、零外部副作用；④ 接线函数的 live 值从 `_mod_*` 读、不留第二个可写来源。探针调用名落地时同步改，**断言条数与语义不变**。
